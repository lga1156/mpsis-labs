# Лаба 4: запуск и защита

## Где должен лежать проект

Vivado должен видеть файлы на том компьютере, где запущен сам Vivado.
Если Ubuntu запускает X2Go, а Vivado открыт на удалённом рабочем столе,
папка нужна на удалённом сервере. Папки только на Mac или в Ubuntu недостаточно.
Передай туда целиком `lab4`, сохранив подпапки `rtl`, `tb`, `mem`, `scripts`.
Можно воспользоваться SFTP с теми же хостом, SSH-портом и логином, что в X2Go.
Пароль вводи в клиенте; в переписку его присылать не нужно.

## Запуск

В Vivado открой `NikitoS.xpr`. Выбери Run Simulation → Run Behavioral Simulation.
В Simulation Sources верхним модулем должен быть `lab_04_tb_CYBERcobra`,
в Design Sources — `CYBERcobra`. Для этого запуска плата не нужна.

Альтернативный способ с чистым проектом: после запуска Vivado, без открытого
проекта, в нижней Tcl Console выполни (замени путь на путь НА СЕРВЕРЕ):

```tcl
source /home/ТВОЙ_ЛОГИН/lab4/scripts/simulate.tcl
```

Скрипт создаёт/пересоздаёт служебный проект `lab4/build_sim`.
Не храни собственные исходники в этой папке.

В конце ожидается `PASS: counter reached 264 and stopped at PC=20`.
Если программа не найдена, проверь наличие `mem/program.mem` в Sources.
Это шестнадцатеричный файл, поэтому в памяти используется `$readmemh`.
После изменения mem-файла сделай Reset Behavioral Simulation и запусти заново.

При запуске через xpr добавь сигналы: Scope → lab_04_tb_CYBERcobra → DUT →
правой кнопкой → Add to Wave Window. Затем Restart и Run All.
Смотри `program_counter`, `instruction`, `read_data1`, `read_data2`,
`write_data`, `branch`, `jump`, `flag`, `out_o`.
Для счётчика удобно выбрать Radix → Unsigned Decimal, для инструкции — Hex.

## Что реализовано

Простой однотактный процессор CYBERcobra: память инструкций, регистровый файл
32×32, АЛУ, PC, сумматор и мультиплексоры. Памяти данных нет.
В течение такта комбинационная логика читает инструкцию, выбирает операнды,
считает результат и следующий PC. На положительном фронте записываются регистры
и новый PC. Сброс синхронный, устанавливает PC=0; регистровый файл не очищает.
Программа сама инициализирует используемые регистры.

Поля инструкции:

| Биты | Значение |
|---|---|
| 31 | J: безусловный переход |
| 30 | B: условный переход |
| 29:28 | WS: 00 — константа, 01 — АЛУ, 10 — переключатели |
| 27:23 | Операция АЛУ (для вычислений/сравнений) |
| 22:18 | RA1: первый регистр-источник, он же источник out_o |
| 17:13 | RA2: второй регистр-источник |
| 12:5 | Знаковое смещение перехода в инструкциях |
| 4:0 | WA: регистр назначения |

Для загрузки константы поле 27:5 трактуется целиком как знаковое число из 23 бит.
Поля перекрываются: их смысл зависит от типа инструкции.

Запись в регистровый файл разрешена, если нет J и B. r0 при чтении всегда равен
нулю и игнорирует запись. `out_o` — комбинационное значение регистра RA1 текущей
инструкции, а не отдельный регистр результата.

## Твоя программа, построчно

| PC (байты, десятичные) | Машинный код | Действие |
|---|---|---|
| 0 | 0FFFFFE1 | r1 = -1 |
| 4 | 20000002 | r2 = знакорасширенные sw_i |
| 8 | 00000023 | r3 = 1 |
| 12 | 10046001 | r1 = r1 + r3 |
| 16 | 4F045FE0 | если r1 < r2 без знака, PC = PC - 4; иначе PC = 20 |
| 20 | 80040000 | переход на себя; RA1=1, поэтому out_o = r1 |

Сначала r1=-1, первое прибавление единицы даёт 0 за счёт 32-битного переполнения.
Дальше счётчик растёт до r2. В тесте sw_i=16'b100001000=264=0x108.
Финал: PC=20=0x14, instruction=0x80040000, out_o=264.
После сброса последовательность PC: 0,4,8,12,16,12,16,…,20,20,…
Начальные X у неинициализированных регистров ожидаемы; в финале X быть не должно.

## Короткие ответы преподавателю

- Почему PC+4? Инструкция 32 бита = 4 байта, адресация побайтовая.
- Зачем адрес памяти срезается до `[8:2]`? Убираем два младших бита,
  чтобы из байтового адреса получить индекс 32-битного слова в памяти 512 байт.
- Откуда берётся следующий PC? Если `J || (B && flag)`, к текущему PC
  прибавляем знаковое смещение ×4; иначе прибавляем 4.
- Почему два нуля справа у смещения? Это умножение на 4. Копии старшего бита
  слева сохраняют знак отрицательного смещения.
- Условный и безусловный переход? Первый зависит от flag АЛУ, второй всегда выполняется.
- Что делает WS? Выбирает источник данных для записи: константу, АЛУ или sw_i.
- Чем HDL отличается от программы? Описывает параллельно работающие блоки схемы;
  программу этот процессор читает из program.mem.
- Почему `<=` в always_ff? Регистры обновляются согласованно на фронте,
  используя значения до фронта. Комбинационную логику описываем assign/always_comb.
- Почему out_o иногда меняется между командами? Его источник задаёт RA1 текущей
  инструкции. Для постоянного финального вывода программа зацикливается на RA1=1.

## Проверка на плате и индивидуальное задание

Методичка требует также проверку на ПЛИС и отдельную программу по варианту.
Сейчас program.mem содержит демонстрационный счётчик, а не индивидуальный вариант.

Для Nexys A7 100T добавь из APS/Labs/04. Primitive programmable device/board files
`nexys_cybercobra.sv` как Design Source и `nexys_a7_100t.xdc` как Constraints.
Назначь верхним модулем Design Sources `nexys_CYBERcobra`, затем Generate Bitstream
и программируй доступную плату через Hardware Manager. Верх симуляции оставь прежним.
Удалённому Vivado требуется доступ к hardware server с подключённой платой.

На плате SW задают вход, BTND выполняет один такт. Для синхронного сброса
удерживай CPU_RESET и нажми BTND. LED показывают младшие 16 бит out_o.
Для короткой демонстрации поставь SW=3 и пройди программу потактово.
Имя экземпляра памяти `imem` и имена её портов нужны обвязке платы.
